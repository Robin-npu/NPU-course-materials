### 2.3仿真执行流程
#### 2.3.1仿真验证流程
本实验采用基于 Cocotb 的自动化验证流程，将 Python 编写的测试激励通过 GPI 接口传递给 Verilator 编译后的 RTL 仿真模型。具体执行流程如下：

1.  **环境初始化**：
    * 启动时钟生成器（Clock Generator），设置周期为 10ns。
    * 驱动 `rst_n` 信号为低电平并保持 2ns，随后拉高，触发 CPU 内部状态（如 PC、寄存器堆）的复位初始化。
2.  **指令与数据预装载**：
    * 在测试脚本中通过 `program` 字典定义 MIPS 汇编机器码，模拟指令存储器（IMEM）。
    * 初始化 `mem` 字典，模拟数据存储器（DMEM）的初始状态。
3.  **单周期迭代执行**：
    * **取指（IF）**：仿真器在每个周期起始采样 `instr_addr`，Python 脚本根据该地址将对应的指令机器码注入 `instr` 端口。
    * **执行与访存（EX/MEM）**：利用 `await Timer(1, units="ps")` 允许 RTL 内部组合逻辑电平在单周期内稳定。
    * **响应监控**：若检测到 `dmem_we` 为高，则同步更新 Python 内存模型 `mem`；若 `dmem_re` 为高，则将 `mem` 中的数据反馈至 `dmem_rdata`。
4.  **结果比对与断言**：
    * 每一条关键指令执行后，通过断言（Assert）检查特定的寄存器值或内存单元数据是否符合预期。
5.  **覆盖率收集**：
    * 仿真结束后，由 Verilator 引擎导出覆盖率数据，通过 `coverage-report` 工具生成可视化的统计报告。

#### 2.3.2测试程序设计流程
本验证平台的核心逻辑由 `tb_cpu_red_top.py` 实现，该脚本基于 Cocotb 异步框架，通过模拟 MIPS 指令序列与内存环境对 DUT 进行全方位测试。

**（1） 指令编码辅助函数（Utility Functions）**
为了提高测试激励的可读性，脚本定义了与 MIPS 指令集对应的编码函数（见第 6-23 行）。这些函数将人类可读的寄存器编号和立即数转换为 32 位二进制机器码：
* `ori(rt, rs, imm)`：封装 ORI 指令的操作码 `0b001101`。
* `addu(rd, rs, rt)`：封装 R 型指令框架及 `0x21` 功能码。
* `bne/lw/sw`：对应 I 型指令的偏移量与基址编码。

**（2） 仿真环境驱动（Test Driver）**
测试主协程 `final_high_coverage` 承担了驱动与监控的双重角色：
* **时钟驱动**：通过 `cocotb.start_soon(Clock(...).start())` 提供恒定的 10ns 时序基准。
* **复位逻辑**：通过 `dut.rst_n.value = 0` 触发异步复位，确保 PC 初始化为 `0x80000000` 且寄存器堆清零。

**（3） 内存模拟逻辑（Memory Emulation）**
脚本通过 Python 字典模拟了单周期处理器的外部存储器环境：
* **指令存储器（IMEM）**：利用 `program` 字典存储指令地址与机器码的映射。在每个周期，根据 `dut.instr_addr` 的输出，实时将指令馈送至 `dut.instr`。
* **数据存储器（DMEM）**：利用 `mem` 字典监控 `dmem_we`（写使能）和 `dmem_re`（读使能）。
    * **写操作**：采样到 `dmem_we` 时，将 `dmem_wdata` 存入 `mem[dmem_addr]`。
    * **读操作**：采样到 `dmem_re` 时，将 `mem` 中的值赋给 `dut.dmem_rdata`。

**（4） 自动化校验与断言（Checking & Assertion）**
程序在执行完预设的 140 个周期后，通过 `assert` 语句进行自动化结果比对：
* **数据一致性**：校验 `mem.get(0x20)` 是否等于写入的 `0xABCD`。
* **分支逻辑**：通过观察 `instr_addr` 的变化，验证 BNE 是否在不等条件下发生了跳转。
* **寄存器保护**：通过针对 `$0` 寄存器的写入指令（如 `emit(addu(0, 3, 4))`），验证 RTL 中的屏蔽逻辑。

**（5） 覆盖率增强策略**
为了达成更高的分支覆盖率，程序在末尾（第 130 行起）特意构造了针对寄存器堆写入边界（如 `rd=0`）的无效操作，以及 BNE 的“跳”与“不跳”两种场景，确保 RTL 中的所有 `if-else` 分支均被激活。。

#### 3.2.2 控制通路译码正确性
本环节旨在通过观测内部控制信号，验证主控制器对不同类型指令的操作码（Opcode）和功能码（Funct）的识别精度。

**1. 译码逻辑实现概述**
根据 `cpu_red_top.v` 源码，控制通路采用纯组合逻辑译码。例如：
* **R型指令识别**：通过 `(opcode == 6'b000000) && (funct == 6'b100001)` 准确锁定了 ADDU 指令。
* **写使能逻辑**：`RegWrite` 信号通过一个多分支的 `always @(*)` 块实现，仅在 ORI、ADDU、LW 指令周期内拉高。

**2. 关键指令译码波形分析**

* **ADDU 指令 (R-Type)**：
    * **输入**：`instr = 0x00643021`（addu $6, $3, $4）。
    * **观测点**：当 `opcode` 为 0 且 `funct` 为 `0x21` 时，观测到寄存器堆的目标寄存器选择端口自动切换至 `rd`（即 6 号寄存器）。
    * **结论**：验证了 R 型指令独有的三寄存器寻址译码正确。

* **ORI 指令 (I-Type)**：
    * **输入**：`instr = 0x34011234`（ori $1, $0, 0x1234）。
    * **观测点**：`ALUSrc` 信号在当前周期被置为 1（选择立即数作为 ALU 第二操作数），同时 `imm_zero` 扩展模块输出 `0x00001234`。
    * **结论**：验证了主控制器能准确区分立即数类型指令，并正确切换 ALU 数据源。

* **访存指令 (LW/SW)**：
    * **输入**：`0x8C...` (LW) 或 `0xAC...` (SW)。
    * **观测点**：对于 LW，`MemtoReg` 信号有效，强制将 `dmem_rdata` 路由至寄存器写回端；对于 SW，`dmem_we` 信号有效。
    * **结论**：验证了控制通路对内存读写使能信号（dmem_re/we）的逻辑互斥控制完全正确。

#### 3.2.4 存在问题及修改情况
在 Phase1 的仿真验证过程中，主要发现了以下两个设计与验证层面的问题，均已完成定位与修复：

##### 问题一：通用寄存器堆 $0 寄存器被意外写入
* **问题现象**：在执行类似 `ori $0, $1, 0x1234` 的指令时，波形显示 `$0` 通用寄存器的值被改写为了 `0x1234`。在 MIPS 架构中，`$0` 应当恒为 0。
* **原因分析**：查看 `cpu_red_top.v` 初版代码，在写回阶段（Write Back）仅判断了写使能 `RegWrite == 1`，未对目标寄存器地址进行有效性检查。
* **修改方案**：
  在 Verilog 中对寄存器写使能条件增加地址判定，并且在时钟复位块中强制规约：
  ```verilog
  // 修改后代码
  assign reg_write_en = RegWrite && (write_reg_addr != 5'b0); // 只有当写地址不为0时才使能

##### 问题二：BNE 指令跳转地址计算错误（未按字对齐左移）
* **问题现象**：在仿真测试 BNE 指令（如负向循环跳转）时，波形显示程序指针 PC 跳转到了一个奇怪的地址，并没有跳到预期的汇编标号处，导致程序跑飞。
* **原因分析**：查看 `cpu_red_top.v` 初版代码，在计算 BNE 的目标跳转地址时，直接将 16 位符号扩展后的立即数与 `PC + 4` 相加。在 MIPS 架构中，分支偏移量代表的是“指令字数”而非“字节数”，计算时物理地址必须向左移 2 位（即乘以 4）。
* **修改方案**：
  在 Verilog 的 `next_pc` 生成逻辑中，对符号扩展后的立即数（`imm_ext`）进行拼接左移 2 位处理：
  ```verilog
  // 修改前代码：直接相加，导致跳转字节地址错误
  assign next_pc = bne_taken ? (pc_plus_4 + imm_ext) : pc_plus_4;

  // 修改后代码：低位补 00（等效于乘以4），实现标准字对齐
  assign next_pc = bne_taken ? (pc_plus_4 + {imm_ext[29:0], 2'b00}) : pc_plus_4;
